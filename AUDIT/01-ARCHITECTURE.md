## 1. What this repository actually is

Three independently-built applications served under one origin:

| # | Project | Path | Build | Serves |
|---|---------|------|-------|--------|
| 1 | Marketing / SEO site | `next-app/` | Next.js 16.3.0 (App Router) | everything except `/app/*` |
| 2 | Booking app (SPA) | `app/` | Vite 8 + React 19 + react-router-dom 7 | `/app/*` |
| 3 | Backend functions | `supabase/functions/` | Deno (Supabase Edge Functions) | called by (2) only |

The SPA is built with `base=/_spa/` by `scripts/build-spa.mjs`, copied into
`next-app/public/_spa`, and rewritten onto `/app/*` by `next.config.ts`. It is therefore a
**committed build artifact** (`next-app/public/_spa/assets/index-BXK52Lnq.js`, 558 KB) that
must be regenerated by hand whenever `app/` changes.

There is no monorepo tool. The root `package.json` is a script shim; `next-app/` and `app/`
have separate lockfiles, separate React installs and separate `@supabase/supabase-js`
versions (2.112.2 vs 2.106.0).

## 3. Frontend map — Next.js site

**Rendering model.** Every SEO route is statically generated with `dynamicParams = false`.
The only non-static things on the marketing site are `/api/lead` (`force-dynamic`) and
`/og` (edge runtime).

**Client components — exactly two on the entire site:**
- `components/home/SalaryEstimator.tsx` (home page only)
- `components/seo/LeadForm.tsx` (rendered only when `NEXT_PUBLIC_LEADS_ENABLED=true`, i.e. never today)

Everything else — including all CTAs — is server-rendered. CTA click tracking is done by a
single delegated listener in an inline script (`components/shared/Analytics.tsx`) reading
`data-mbm-*` attributes. This is a genuinely good decision and the main reason the site
ships almost no JavaScript.

**Composition engine.** `lib/seo-engine/compose.ts` (967 lines) turns data-layer records
into a `PageModel`; `components/seo/SeoPage.tsx` renders any `PageModel`. The same models
feed the routes, the sitemaps and the quality gate, so what is measured is what is served.

**State:** none. No context, no store, no client cache. Two `useState` hooks in total.

**Loading / error states:** there are no `loading.tsx` or `error.tsx` files anywhere. All
pages are static, so this is defensible for the SEO site — but it also means an unexpected
runtime error in a server component renders Next.js's default error page, unbranded.

## 4. Frontend map — booking SPA

```
main.jsx → BrowserRouter(basename=/app) → AuthProvider → App
  /auth        public                       AuthPage
  /terms       public                       TermsPage
  /splash      public                       SplashScreen   (4-second forced delay)
  /onboarding  Protected                    OnboardingPage
  /            Protected + OnboardingGuard  AppLayout
    home · services · services/:serviceId · bookings · pricing · profile
  *            → /home
```

All state lives in one context (`AuthContext.jsx`), which holds `user`, `profile`,
`userPlan`, `userBookings` and every mutation. There is no data-fetching library, no cache
invalidation strategy, and no optimistic updates: `refreshBookings` / `refreshUserPlan`
re-query on demand.

## 5. Data model — as actually defined in SQL

```
auth.users ──1:1── profiles          (trigger `handle_new_user` copies id + phone only)
     │
     ├──1:N── bookings               (service, city TEXT free-form, notes, status, assigned_helper)
     ├──1:N── user_plans             (plan_name, amount_paid, razorpay_payment_id,
     │                                replacements_total/used, expires_at, is_active)
     └──0:N── email_logs             (RLS on, service-role only)

leads                                 ← PROPOSED ONLY, NOT APPLIED
placement_societies (view)            ← PROPOSED ONLY, depends on columns that do not exist
```

Entities the brief asks about that **do not exist anywhere in this system**:
`Maid`/`Helper`, `Service` (as a table), `Location` (as a table), `Payment` (as a table),
`Notification`, `Replacement`. Services and locations live only in TypeScript files under
`next-app/data/seo/`; helpers exist only as marketing copy.

### The SEO data layer
`next-app/data/seo/` is the single source of truth for locations and money:
8 cities → 35 zones → 342 localities → 267 pincodes; 6 services; 3 plans. It is exported to
the SPA as `app/src/lib/serviceability.json` by `npm run seo:export-spa`. Plan prices flow
`data/seo/plans.ts` → `serviceability.json` → SPA, and are **hand-mirrored** into the two
Razorpay edge functions — a documented but fragile coupling (see `11-PAYMENTS.md` FIN-P05).

| Function | Deployed? | Caller identity check | Purpose |
|---|---|---|---|
| `create-razorpay-order` | yes (200) | yes — `auth.getUser(token)` | server-side order creation |
| `verify-razorpay-payment` | yes (200) | yes — `auth.getUser(token)` | signature check + plan activation |
| `delete-account` | yes (200) | yes — `auth.getUser(token)` | DPDP erasure |
| `send-package-email` | yes (200) | **none** | plan confirmation email |
| `send-booking-email` | yes (200) | **none** | booking confirmation email |
| `send-plan-email` | **no (404)** | none | superseded; not deployed, no caller |

Deployment status verified live by CORS preflight, 2026-09-08. All six run with
`SUPABASE_SERVICE_ROLE_KEY` and therefore bypass RLS entirely.

There are **no background jobs, no queues, no retries and no webhooks**. Razorpay is
integrated callback-only: if the browser closes between payment and the verify call, the
payment is captured by Razorpay and no plan is ever created. See `11-PAYMENTS.md`.

## 7. Infrastructure and trust boundaries

```
Browser
  |
  +- Vercel Edge -- proxy.ts -- canonical host -> legacy redirect map -> maintenance gate
  |     |
  |     +- static prerendered HTML (2,513 SEO pages)        [TB1: none - fully public]
  |     +- /api/lead  (Node runtime, service-role key)      [TB2: server-only secret]
  |     +- /og        (edge, unauthenticated)               [TB3: NONE - see FIN-S05]
  |     +- /_spa/*    static SPA bundle (contains anon key) [public by design]
  |
  +- Supabase (direct from the browser, bypassing Vercel entirely)
        +- auth/v1        [TB4: Supabase Auth]
        +- rest/v1        [TB5: RLS - the ONLY thing protecting user data]
        +- functions/v1   [TB6: gateway JWT (anon key passes) -> per-function check]
```

**The single most important architectural fact in this repository:** the booking app talks
to Supabase *directly from the browser* using a public anon key. Vercel is not in that
path. Therefore **Row Level Security is the entire authorisation layer** for `profiles`,
`bookings` and `user_plans`. Any RLS gap is a direct, internet-facing data exposure.

**TB6 is weaker than it looks.** Supabase's function gateway rejects requests with no
`Authorization` header (verified live: `UNAUTHORIZED_NO_AUTH_HEADER`, HTTP 401), but it
accepts the **anon key**, which is served to every visitor inside
`/_spa/assets/index-BXK52Lnq.js`. Verified live: presenting that key reaches function code.
So "gateway-protected" means "protected from nobody who can view-source".

## 8. Architectural assessment

**Genuinely good, and worth protecting:**
- One source of truth for locations and money, mechanically exported to every consumer.
- Server-rendered CTAs with delegated tracking — near-zero JS across 2,513 pages.
- Payment amounts resolved server-side from a server-held plan table; the client cannot set a price.
- A quality gate that can mark a page `noindex` without failing the build.
- A redirect map that collapses `.html` legacy URLs to clean URLs in a single hop.
- `dropUnverified()` — unverified claims are withheld rather than asserted. Rare discipline.

**Structurally expensive as the business grows:**

1. **Two front-ends, two design systems, two auth models, one product.** The SEO site knows
   nothing about the user; the SPA knows nothing about the page the user came from. The CTA
   handoff between them is broken today (FIN-B02) and there is no shared session.
2. **The SPA build is a committed artifact.** Nothing enforces that `public/_spa` matches
   `app/src`. It happens to be current today; nothing guarantees it tomorrow.
3. **Business rules live in three places.** Plan prices: `plans.ts`, `serviceability.json`,
   and hand-copied into two Deno files. Replacement counts: `plans.ts`,
   `user_plans.replacements_total`, and re-stated in three email templates.
4. **No service layer.** `AuthContext.jsx` is simultaneously the auth provider, the data
   layer, the cache and the mutation API for the whole booking app.
5. **The trust claims have no system behind them.** No helpers table, no verification
   record, no replacement workflow. See `16-CONTENT.md` FIN-C04 / FIN-C05.
